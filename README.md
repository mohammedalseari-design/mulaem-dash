# نظام ملائم العقاري — لوحة المشاريع (mulaem-dash)

واجهة النظام كما كانت في `dash.mulaem.sa`، مع استبدال الباك-إند القديم (PHP + MySQL على GoDaddy) بـ **Supabase**، واستضافة الواجهة كملفات ثابتة (GitHub Pages أو أي استضافة ثابتة).

## لماذا التغيير

الـAPI القديم كان يرد على أي طلب بدون تسجيل دخول (الجلسة في المتصفح فقط). هنا كل التحقق والصلاحيات في السيرفر:
تسجيل الدخول عبر Supabase Auth، والصلاحيات عبر Row Level Security، وإدارة الحسابات عبر دالة خاصة بالمدير.

## محتوى المستودع

| المسار | الوصف |
|---|---|
| `index.html` | الباب الواحد: الرابط الأساسي يحوّل إلى النظام `crm/index.html#/work` («عملي اليوم») |
| `projects.html` | صفحة المشاريع والخريطة (كانت `index.html`) — تحمّل مكتبة Supabase و`config.js` و`supabase-shim.js`. لوحة التحكم القديمة فيها صارت في النظام: `#/approvals` و`#/users` و`#/activity` |
| `crm/` | النظام: العملاء والعقارات والمواعيد والصفقات والإدارة |
| `css/style.css`, `images/logo.jpg` | بدون تغيير |
| `js/script.js` | منطق الواجهة الأصلي **بدون أي تعديل** (ما زال ينادي `api/*.php`) |
| `js/supabase-shim.js` | يعترض نداءات `api/*.php` ويحوّلها إلى Supabase ويرجع نفس شكل الردود القديمة |
| `js/config.js` | رابط المشروع والمفتاح العام (آمن للنشر). **لا يوضع فيه مفتاح الخدمة أبداً** |
| `supabase/migrations/001_init.sql` | الجداول + RLS + المشغّلات + حاوية الصور |
| `supabase/functions/admin-users/` | دالة Edge لإنشاء الموظفين وتغيير كلمات المرور والحظر والحذف (للمدير فقط) |
| `supabase/functions/agent-run/` | دالة Edge للمساعد الذكي (الجولة B): تقرأ مرفقات الطلب من المخزن الخاص، تستخرج الحقول بـ Claude بمخطط JSON صارم، تتحقق منها مستقلاً، وتكتب مسودات فقط. تعمل خلف `ANTHROPIC_API_KEY` (سر في Supabase، لا في المستودع)؛ بدونه تُظهر «الاستخراج التلقائي غير مفعّل» ويفشل الطلب بهذا السبب |

## واجهة النظام: التصميم السادس «الوسيط» (2026-10-23)

طبقة أنماط أخيرة `crm/v6.css` فوق `easy.css` و`v5.css` (وتُحمَّل في `projects.html` أيضاً)، وخط عربي واحد هو IBM Plex Sans Arabic.
الأبواب الخمسة كما هي، وفي داخلها أقسام عمل الوسيط:

| الباب | الأقسام والمسارات | المصدر في قاعدة البيانات |
|---|---|---|
| «عملي اليوم» `#/work` | أرقام: المتأخرة، مواعيد اليوم، المعاينات القادمة (7 أيام)، العملاء المحتملون، الصفقات الجارية، العمولات غير المحصّلة؛ ولوحات: المتأخرة، اليوم، المعاينات القادمة، صفقات تحتاج متابعة (لمركز الاتصال: طلبات جديدة) | `v_my_work`، `follow_ups` (قناة `visit` = معاينة)، `client_requirements`، `deals`، `commissions` |
| «العملاء» `#/clients` | العملاء بفئاتهم (مشترون، مستأجرون، ملاك وبائعون، مستثمرون) مع الطلبات المفتوحة والمتابعة القادمة · `#/requests` طلبات الشراء والإيجار · `#/matches` المطابقات | `v_clients_overview` (يعود إلى `clients` إن لم يوجد)، `client_requirements`، `property_matches` |
| «العقارات» `#/properties` | للبيع / للإيجار ومرشّحات الحي والسعر | `v_units` |
| «الصفقات» `#/deals` | شريط المراحل فوق اللوحة · `#/commissions` العمولات (لا يراها مركز الاتصال) | `deals`، `commissions`، `commission_payments` |

- البحث السريع `crm/js/palette.js`: Ctrl+K أو «/» أو حقل البحث في الشريط العلوي (وعلى الجوال زر البحث أعلى «عملي اليوم» وفي «المزيد»): العملاء بالاسم أو الجوال، والعقارات بالاسم أو الحي، والصفحات.
- الأقسام الجديدة قراءة فقط؛ كل كتابة تبقى في مكانها القديم (ملف العميل، صفحة الطلب، صفحة الصفقة) وبسياسات RLS نفسها.
- حالات الشاشة في `crm/js/ui.js`: `empty(نص، شرح، إجراء)`، و`errorBox(خطأ، بادئة، إعادة)` بزر «إعادة المحاولة»، ورسائل الشبكة والجلسة بالعربية، وشريط انقطاع الإنترنت.

## الصلاحيات (مفروضة في قاعدة البيانات)

| الدور | يرى | يضيف | يعدّل / يحذف |
|---|---|---|---|
| `admin` | كل المشاريع + المستخدمين + سجل النشاط | نعم (يُعتمد مباشرة) | كل شيء، ويعتمد/يرفض |
| `field` | المعتمد + مشاريعه هو | نعم (يدخل "معلق" حتى يعتمده المدير) | مشاريعه فقط (التعديل يعيدها "معلق")، ويحذف غير المعتمد منها |
| `callcenter` | المعتمد فقط | لا | لا |
| حساب معطَّل | لا شيء | لا | لا |

صاحب المشروع وحالته واسم الموظف في سجل النشاط يحددها السيرفر من هوية الحساب، ولا يُقبل ما يرسله المتصفح.

الصفقات والعمولات: الوسيط يرى صفقاته وعمولاتها فقط، ويسجّل قيمة الصفقة قبل الإتمام ويؤكد السعر النهائي عنده. صفقة «تمت» لا يعيد فتحها ولا يعدّل قيمتها إلا المدير (`034_won_deal_admin_lock.sql`)، والعمولات ودفعاتها يكتبها المدير وحده.

## التشغيل من الصفر

1. أنشئ مشروع Supabase، ثم نفّذ `supabase/migrations/001_init.sql` في SQL Editor.
2. استورد البيانات (ملف `002_import_data.sql` — غير موجود في المستودع عمداً لأنه بيانات عمل).
3. انشر الدالتين: `supabase functions deploy admin-users` و`supabase functions deploy agent-run --no-verify-jwt` (الثانية تتحقق من الهوية داخلها: رمز جلسة المستخدم، أو سر pg_cron من Vault).
   ثم ضع مفتاح OpenRouter سراً: `supabase secrets set OPENROUTER_API_KEY=...` — قبل ذلك يعمل كل شيء إلا الاستخراج نفسه (`docs/ROUTER.md`).
4. ضع رابط المشروع والمفتاح العام في `js/config.js`.
5. أنشئ أول مدير: من Authentication ← Add user، بإيميل بصيغة `username@users.mulaem.sa`، ثم:
   ```sql
   insert into profiles (id, username, fullname, role)
   select id, 'username', 'الاسم الكامل', 'admin' from auth.users where email = 'username@users.mulaem.sa';
   ```
6. بقية الموظفين يضيفهم المدير من تبويب المستخدمين داخل النظام (كلمة المرور 8 خانات فأكثر). إذا استُخدم نفس اسم المستخدم القديم يُحافَظ على رقمه وترتبط به مشاريعه القديمة.

## الدخول باسم المستخدم

Supabase Auth يعمل بالإيميل، فاسم المستخدم `ali` يُحوَّل داخلياً إلى `ali@users.mulaem.sa` (لا يلزم بريد حقيقي). اسم المستخدم المكتوب كإيميل يُستخدم كما هو.

## اختبارات

- `tests/*.test.js` و`tests/*.test.mjs`: تطابق الردود مع شكل الـAPI القديم، ومحلّل تصدير واتساب، وفرز واتساب، والمكررات في الاعتماد (`node <الملف>` لكل ملف؛ آخر سطر ملخص بصفر فشل).
- صلاحيات RLS مُختبرة على PostgreSQL 16 (24 حالة: مجهول، مدير، ميداني، كول سنتر، معطَّل).
- `supabase/functions/**/*.test.ts`: التحقق المستقل من ناتج النموذج والمحتوى المريب وحدود المرفقات وفتح الروابط وموجّه الجهد وفرز واتساب (`deno test --allow-read --allow-env supabase/functions/`) — بلا شبكة ولا مفتاح. مع `deno check` لكل `supabase/functions/*/index.ts` و`deno lint supabase/functions`.
- هذه الأوامر نفسها هي بوابة GitHub Actions على كل دفعة وطلب دمج (`.github/workflows/tests.yml`).
